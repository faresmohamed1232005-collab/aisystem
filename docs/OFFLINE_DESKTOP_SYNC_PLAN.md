# خطة: تطبيق سطح مكتب (Offline-First) + مزامنة + تحديث تلقائي

> **الهدف:** تحويل نظام الصيدلية (Laravel 12 + MySQL) إلى تطبيق سطح مكتب (.exe) يعمل بالكامل
> بدون إنترنت، ويتزامن مع السيرفر المركزي عند توفّر النت، ويستقبل تحديثات الكود تلقائياً.
>
> **القرارات المتفق عليها:**
> - السيناريو: **فروع متعددة**، و**كل فرع له مخزونه المستقل تماماً** (لا مخزون مشترك).
> - **السيرفر = مصدر الحقيقة (master)**.
> - **قاعدة الفرع = SQLite** (المسار الرسمي لـ NativePHP — لا يحزم MySQL). السيرفر = MySQL.
> - أداة التغليف: **NativePHP** (يأخذ Laravel كما هو ويبنيه .exe). راجع قسم «إيضاح NativePHP».
> - البدء: **هذه الخطة المعمارية الكاملة أولاً** قبل أي كود.

---

## 0) إيضاح: NativePHP و«تحويل Laravel إلى exe»

- لا يوجد «تحويل Laravel إلى exe» قائم بذاته: Laravel كود PHP يحتاج مفسّراً وخادماً ليعمل.
- **NativePHP** (وليس «PHP native») هو غلاف يأخذ **مشروع Laravel كما هو** ويحزم معه:
  مفسّر PHP + خادم محلي + نافذة سطح مكتب + قاعدة SQLite، ويُخرج **ملف .exe واحد**.
- تكتب Laravel عادياً تماماً؛ NativePHP طبقة تغليف فقط، ليس بديلاً عن Laravel.

### لماذا SQLite وليس MySQL على الفرع؟
- **NativePHP لا يحزم MySQL** (أسباب ترخيص، رسمياً وغالباً لن يدعمه). البدائل:
  1. **SQLite** (المعتمد): يعمل تلقائياً، ملف واحد، صفر إعداد، ترحيل تلقائي لكل إصدار. ✅
  2. MySQL مثبّت يدوياً على كل جهاز: تطابق كامل لكن عبء تثبيت/تشغيل على كل فرع. ❌ مرهق.
  3. MySQL بعيد خلف API: **يكسر شرط offline** — مرفوض. ❌
- المصادر: nativephp.com/docs (Databases)، NativePHP Discussion #567.

### بوابة توافق SQLite (مسح فعلي للكود — الحجم صغير ومحدود)
الـ raw SQL في المشروع معظمه متوافق مع SQLite (`COALESCE`, `DATE()`, `CAST`, `SUM`, `COUNT`,
`SUBSTRING` بسيطة). التعديلات المطلوبة قليلة ومحصورة:
| تعبير MySQL | البديل في SQLite | أين (تقريباً) |
|-------------|------------------|----------------|
| `YEAR(expense_date)` | `strftime('%Y', expense_date)` | ExpenseController |
| `SUBSTRING(code, 5)` / `CAST(SUBSTRING(...))` | `substr(code, 5)` / `CAST(substr(...))` | Customer/Supplier (ترقيم الأكواد) |
| `DATE_FORMAT(...)` إن وُجد | `strftime(...)` | تقارير |
> الحل: طبقة مساعدة (helper) تختار التعبير حسب نوع الاتصال، أو توحيد على دوال متوافقة.
> هذا المسح يثبت أن المخاطرة محدودة وقابلة للإدارة.

## 1) الصورة الكبيرة (المعمارية)

```
┌─────────────────────────────────────────────────────────────┐
│                    السيرفر المركزي (Master)                   │
│   Laravel 12 + MySQL  +  Sync API  +  Update/Release feed     │
└───────────────▲──────────────────────────▲──────────────────┘
                │ (push/pull عند توفّر النت)  │
        ┌───────┴────────┐          ┌────────┴───────┐
        │   فرع A (.exe)  │          │   فرع B (.exe)  │
        │ Laravel محلي    │          │ Laravel محلي    │
        │ + SQLite/MySQL  │          │ + SQLite/MySQL  │
        │ يعمل offline    │          │ يعمل offline    │
        └────────────────┘          └────────────────┘
```

كل فرع يشغّل **نسخة كاملة من Laravel محلياً** بقاعدة بيانات محلية. البيع/الشراء يحدث محلياً
دائماً (حتى بدون نت). خدمة مزامنة في الخلفية تدفع تغييرات الفرع للسيرفر وتسحب تغييرات
السيرفر عند توفّر الاتصال.

## 2) المراحل (Roadmap)

| المرحلة | المحتوى | الحالة |
|---------|---------|--------|

### ما أُنجز فعلياً في P4 (تمّت ومُختبَرة)
- جدول `sync_logs` + `SyncStatus`: تسجيل كل دورة (push/pull) مع تشذيب (آخر 200 سجل).
- **Backoff تصاعدي** (exponential، سقف 15د): بعد فشل متكرر يؤجّل التشغيل التلقائي، والنجاح
  يصفّره. التشغيل اليدوي يتجاهل الـ backoff. لا يفقد أي تغيير (synced_at لا يُحدَّث إلا بنجاح).
- `SyncRunner`: ينسّق Push+Pull مع تسجيل وحالة وbackoff. يستخدمه الزر اليدوي و`sync:run`.
- **مؤشر اتصال** في الـ layout: لون أيقونة الزر (أخضر=online، أحمر=offline) + tooltip بآخر نجاح،
  polling كل 15ث عبر `/sync/status`.
- **نسخ احتياطي محلي** `sync:backup`: ينسخ ملف SQLite للفرع بطابع زمني، يحتفظ بآخر 14 نسخة.
- جدولة (routes/console.php عند sync.enabled): `sync:run` كل دقيقة (withoutOverlapping)،
  `sync:backup` يومياً 3:17 فجراً.
- اختبارات: backoff (يمنع/يتصاعد/يتصفّر ✓)، logging ✓، state ✓.

> **المشروع مكتمل (P0→P4).** يتبقّى للنشر الفعلي: ملء مفاتيح env على السيرفر/الفرع
> (SYNC_*, GITHUB_*)، بناء الـ .exe (`native:build`)، ورفع أول Release على GitHub.

### ما أُنجز فعلياً في P2 (تمّت ومُختبَرة)
- **Push** (فرع → سيرفر): `SyncPushService` يجمع صفوف pendingSync، يترجم الـ FK من id → uuid،
  يرفعها لـ `/api/sync/push`، ويعلّم synced_at. `SyncController@push` يطبّق بترتيب التبعيات
  داخل معاملة، يترجم uuid → id، ويعمل upsert.
- **Pull** (سيرفر → فرع): `/api/sync/pull` يرجّع تغييرات الكتالوج (drugs, ads) منذ cursor.
  `SyncPullService` يطبّقها محلياً مع markSynced لمنع echo-loop. جدول `sync_state` يخزّن cursor.
- مصادقة `X-Sync-Token` عبر middleware `sync.auth` (اختُبرت: 401/200).
- أوامر: `sync:push`, `sync:pull`, `sync:run` (دورة كاملة، تُجدوَل دورياً).
- زر مزامنة يدوي + تلقائي دوري في الـ layout (config sync.enabled).
- اختبارات: ترجمة FK (MATCH ✓)، upsert، منع echo-loop (pendingSync لا يلتقط المسحوب ✓).

### ما أُنجز فعلياً في P3 (تمّت ومُختبَرة)

## 3) P0 — تجهيز قاعدة البيانات للمزامنة (الأهم والأخطر)

المشكلة الجذرية الحالية: كل الجداول تستخدم `$table->id()` (auto-increment). لو الفرع A أنشأ
بيعة `id=50` والسيرفر أيضاً `id=50` → تصادم وفساد بيانات. الحل المعتمد عالمياً:

### 3.1 معرّف عالمي (UUID/ULID) لكل صف قابل للمزامنة
- نضيف عمود `uuid` (ULID) **فريد** لكل جدول يُزامَن (sales, sale_items, drugs, products,
  purchase_invoices, suppliers, customers, ...).
- نُبقي `id` المحلي auto-increment للأداء والعلاقات الداخلية، لكن **المزامنة والربط بين
  الأجهزة تتم عبر `uuid`** لا عبر `id`.
- العلاقات بين الجداول في طبقة المزامنة تُرسَل بالـ `uuid` (مثلاً `sale_uuid` للبند).

### 3.2 أعمدة تتبّع المزامنة (على كل جدول قابل للمزامنة)
```php
$table->ulid('uuid')->unique();          // المعرّف العالمي
$table->string('origin_branch')->nullable();   // الفرع الذي أنشأ الصف
$table->timestamp('synced_at')->nullable();    // آخر مزامنة ناجحة
$table->softDeletes();                    // deleted_at — حذف ناعم (المزامنة تحتاجه)
// timestamps() موجودة بالفعل (created_at / updated_at) — سنستخدم updated_at كعلامة تغيير
```

### 3.3 هوية الفرع
- كل تثبيت (.exe) يحصل على `branch_id` ثابت عند أول تشغيل (يُسجَّل لدى السيرفر).
- يُخزَّن في إعداد محلي ويُوسَم به كل صف يُنشأ في هذا الفرع (`origin_branch`).

### 3.4 ترقيم الفواتير بدون تصادم
- `invoice_number` حالياً `unique`. مع عدة فروع سيتصادم.
- الحل: **بادئة الفرع** في رقم الفاتورة (مثل `A-1001`, `B-1001`) أو نطاقات أرقام لكل فرع.

> **مخرجات P0:** Migration واحدة تضيف الأعمدة أعلاه + Trait `Syncable` على الـ Models
> (يولّد UUID تلقائياً عند الإنشاء، يضبط origin_branch) + Backfill للصفوف الموجودة.

## 4) P1 — تغليف سطح المكتب (Offline)

### الأداة الموصى بها: **NativePHP** (نفس فريق Laravel ecosystem)
يأخذ تطبيق Laravel كما هو ويبنيه كـ `.exe` لويندوز، يحزم PHP + خادم محلي، ويدعم
auto-update. بديل: Electron + خادم PHP محلي (أعقد).

### قاعدة البيانات المحلية: خياران
| الخيار | مزايا | عيوب |
|--------|-------|------|
| **SQLite** (موصى به للفرع) | ملف واحد، صفر إعداد، يُحزم بسهولة | اختلافات SQL بسيطة عن MySQL |
| **MySQL محلي** | مطابق للسيرفر تماماً | تثبيت/تشغيل MySQL على كل جهاز = صداع |

> توصية: **SQLite محلياً على الفرع، MySQL على السيرفر**. نراجع الـ migrations لضمان
> توافقها مع SQLite (معظمها متوافق، نتحقق من أي raw SQL).

### مخرجات P1
- التطبيق يفتح كنافذة سطح مكتب، يعمل بالكامل offline على قاعدة محلية.
- شاشة إعداد أولى: ربط الفرع بالسيرفر (URL + مفتاح الفرع) — تعمل لاحقاً، البيع لا ينتظرها.

## 5) P2 — طبقة المزامنة (قلب المشروع)

### 5.1 النمط: Outbox + Pull/Push عبر REST
- **Outbox (صندوق صادر):** كل تغيير محلي (إنشاء/تعديل/حذف ناعم) يُسجَّل في جدول
  `sync_outbox` (نوع الجدول، uuid، العملية، الحمولة، الطابع الزمني).
- **Push:** عند توفّر النت، خدمة خلفية ترسل دفعات الـ outbox للسيرفر؛ السيرفر يطبّقها
  ويردّ بالمقبول/المرفوض؛ نمسح المقبول من الـ outbox.
- **Pull:** الفرع يطلب من السيرفر «أعطني كل ما تغيّر منذ آخر مزامنة (cursor)» ويطبّقه محلياً.

### 5.2 حل التعارضات (السيرفر master)
- **القاعدة الأساسية:** عند تعارض على نفس `uuid`، **السيرفر يكسب** للسجلات المرجعية
  (الأدوية، الموردين، العملاء، الأسعار).
- **السجلات المعاملاتية (مبيعات/مشتريات):** هذه **append-only** — كل بيعة لها uuid فريد من
  الأساس، فلا تتعارض؛ تُدمج كلها. لا «تحديث» متزامن على نفس البيعة من جهازين.
- **المخزون (الكمية):** لا نزامن «الكمية النهائية» (تتصادم)، بل **نزامن حركات المخزون**
  (كل بيعة/شراء = حركة −/+) ويُعاد احتساب الرصيد. هذا يمنع ضياع المخزون. ← قرار مهم.

### 5.3 ما الذي يُزامَن في أي اتجاه؟
| البيانات | الاتجاه | الفائز عند التعارض |
|----------|---------|---------------------|
| كتالوج الأدوية/الأسعار/الموردين | سيرفر → فرع (أساساً) | السيرفر |
| المبيعات/المشتريات (معاملات) | فرع → سيرفر | لا تعارض (uuid فريد) |
| مخزون الفرع | فرع → سيرفر (لكل فرع سجله) | لا تعارض (مخزون مستقل) |
| المستخدمون/الصلاحيات | سيرفر → فرع | السيرفر |

> **ملاحظة مهمة (نتيجة قرار «مخزون مستقل لكل فرع»):** بما أن كل فرع له مخزونه الخاص،
> فلا يوجد تعارض على كمية صنف واحد بين فرعين. مخزون الفرع يُرفع للسيرفر **كصورة خاصة بهذا
> الفرع** (مفهرسة بـ `branch_id`)، والسيرفر يجمّعها للعرض فقط. هذا يلغي أصعب جزء في
> المزامنة (تعارض الكميات) ويجعل المخزون append/branch-scoped بدلاً من دمج معقّد.
> ملاحظة: جدول `user_drug_inventory` الحالي يربط المخزون بالمستخدم — نتأكد أن وسم الفرع
> (`branch_id`) يميّز مخزون كل فرع على السيرفر.

### 5.4 أمان الـ Sync API
- مصادقة كل فرع بمفتاح (Sanctum token لكل فرع)، HTTPS، تحقق من `branch_id`.

> **مخرجات P2:** جداول `sync_outbox` + `sync_state` (cursor)، Sync API على السيرفر
> (`/api/sync/push`, `/api/sync/pull`)، خدمة مزامنة دورية على الفرع، شاشة حالة المزامنة.

## 6) P3 — التحديث التلقائي (الكود + الداتابيز)

### 6.1 تحديث الكود
- **NativePHP Auto-Updater:** عند توفّر النت يفحص «خلاصة الإصدارات» (release feed) على
  السيرفر؛ لو فيه نسخة أحدث → يظهر للمستخدم «يوجد تحديث» → ينزّله ويثبّته ويعيد التشغيل.
- ترقيم إصدارات (مثل `1.4.2`) + ملف توقيع للأمان.

### 6.2 ترحيل قاعدة البيانات تلقائياً
- بعد كل تحديث كود، عند الإقلاع: `php artisan migrate --force` تلقائياً على القاعدة المحلية.
- المايجريشنز تُكتب بحذر (إضافات غير كاسرة) كي لا تُفسد بيانات الفرع.

### 6.3 إشعار التحديث
- شارة/بانر «يوجد تحديث (v1.4.2)» بمجرد اكتشاف النت لنسخة أحدث، مع زر «تحديث الآن».

> **مخرجات P3:** قناة إصدارات على السيرفر، فحص دوري للنسخة، تطبيق المايجريشن تلقائياً
> بعد التحديث، واجهة إشعار/تحديث.

## 7) P4 — الصلابة والتشغيل

- **قائمة انتظار + إعادة محاولة** للمزامنة الفاشلة (backoff)، لا تفقد أي تغيير.
- **سجلّ مزامنة** (نجاح/فشل/تعارض) يراه المستخدم.
- **مؤشر اتصال** (متصل/غير متصل/يتزامن الآن).
- **نسخ احتياطي محلي** دوري لقاعدة الفرع.
- اختبارات: محاكاة قطع النت، بيع offline ثم مزامنة، تعارض كتالوج، تحديث نسخة.

## 8) المخاطر الكبرى (يجب الانتباه لها)

1. **فساد بيانات المخزون** = الخطر الأول. الحل: مزامنة الحركات لا الأرصدة (5.2).
2. **تصادم المعرّفات** → UUIDs (P0) تحلّها جذرياً.
3. **تصادم أرقام الفواتير** → بادئة الفرع (3.4).
4. **اختلاف SQLite عن MySQL** → مراجعة الـ migrations وأي raw SQL.
5. **مايجريشن كاسرة على بيانات الفرع** → سياسة «إضافات غير كاسرة فقط».
6. **حجم البيانات الأولى** → أول مزامنة قد تكون كبيرة؛ نحتاج تنزيل دفعي أولي (seed).

## 9) القرارات (المحسوم منها والمتبقّي)

**محسومة:**
- [x] قاعدة الفرع: **SQLite** (السيرفر MySQL).
- [x] أداة التغليف: **NativePHP**.
- [x] المخزون: **لكل فرع مخزونه المستقل** — لا مخزون مشترك. (يبسّط المزامنة كثيراً، انظر 5.2)

**محسومة (إضافية):**
- [x] **ترقيم الفواتير:** بادئة الفرع — `{BRANCH_CODE}-{seq}` (مثل `A-1001`). كل فرع له عدّاده
      المحلي المستقل، والبادئة تمنع التصادم عالمياً. يُطبّق على المبيعات والمشتريات.
- [x] **دورية المزامنة:** **تلقائية دورية** (افتراضي كل ~60 ثانية عند توفّر النت) **+ زر مزامنة
      يدوي** + مزامنة عند الإقلاع. قابلة للضبط لاحقاً.
